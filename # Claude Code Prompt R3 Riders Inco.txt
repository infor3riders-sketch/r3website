## Architecture: one app, two "sites" via host-based routing

Single Next.js app with host-based routing in `middleware.ts`:

- Public host requests rewrite to `app/(site)/...`
- Portal host requests rewrite to `app/(portal)/...`
- Local dev: `localhost:3000` is the public site; `portal.localhost:3000` is the portal. Document in README.
- Hostnames come from env vars (`NEXT_PUBLIC_SITE_HOST`, `NEXT_PUBLIC_PORTAL_HOST`).
- Cross-access blocked: portal routes unreachable on the public host and vice versa (404).
- Separate root layouts, nav and theme tokens per route group. No imports from `(portal)` into `(site)` or the reverse.

```
src/
  app/
    (site)/            # public website
    (portal)/          # member portal
    api/               # webhooks, cron
  components/
    ui/                # shared primitives
    site/
    portal/
  lib/
    supabase/          # browser, server, middleware clients
    auth/              # role helpers, guards
    payments/          # PaymentProvider interface + adapters
    validators/        # zod schemas
  server/              # server actions, queries
  emails/
supabase/
  migrations/
  seed.sql
docs/
  design/home-reference.png
```

Roles (enum): `member`, `officer`, `admin`.

Modules:

## Payments

Build a `PaymentProvider` interface in `src/lib/payments/` used by both the Shop and Donations.

- **v1 default: manual provider.** Checkout/donation shows the organization's payment instructions (GCash number/QR, bank details from `site_settings`), collects a reference number and optional proof-of-payment image upload, and creates the record as `pending`. Officers verify in the portal, which flips status to `paid` and triggers emails and stock decrement.
- **Gateway-ready:** also scaffold a `paymongo` adapter (GCash, Maya, cards) behind env flag `PAYMENT_PROVIDER=manual|paymongo`, including a signed webhook route handler that marks orders/donations paid. Keep it disabled by default and document what keys are needed.
- Never store card data. Never trust client-reported payment success; status changes happen only server-side (officer action or verified webhook).
- Stock is reserved at order creation and released if the order is cancelled or expires.

## Supabase (one project)

- All schema changes as SQL in `supabase/migrations/` via Supabase CLI. No dashboard-only changes.
- Core tables (adjust as needed): `profiles`, `motorcycles`, `membership_types`, `applications`, `events`, `event_rsvps`, `event_attendance`, `programs`, `volunteer_signups`, `announcements`, `announcement_reads`, `news_posts`, `gallery_albums`, `gallery_photos`, `dues_periods`, `dues_payments`, `documents`, `products`, `product_variants`, `product_images`, `orders`, `order_items`, `discount_codes`, `donation_campaigns`, `donations`, `payments`, `contact_messages`, `audit_log`, `site_settings`.
- **RLS on every table**, with explicit policies:
  - anon: read rows where `is_public = true` (events, programs, news, gallery, active products, active campaigns); INSERT only into `applications`, `contact_messages`, `volunteer_signups`, and via server-side routes for `orders` and `donations`. Orders and donations are never readable by anon; lookups happen through signed tokens in server code.
  - members: own profile, RSVPs, payments, volunteer signups; directory per privacy flags
  - officers: manage events, programs, announcements, attendance, applications, payment verification, shop, donations
  - admins: everything, including role changes
  - A user can never escalate their own role (policy or trigger)
- Helper functions `is_officer()` and `is_admin()` (security definer, stable)
- Triggers: create `profiles` row on `auth.users` insert, `updated_at`, audit logging on sensitive tables
- Storage buckets: `public-media` (site images, product images), `member-avatars`, `payment-proofs` (private), `documents` (private). Enforce size limits and MIME types.
- Generate TypeScript types (`supabase gen types`) and use them everywhere.
- Service role key only in server-side code and only where RLS bypass is truly required (invites, webhooks, order/donation creation for guests).
- `seed.sql` with demo data, clearly marked dev-only.

## Security and quality

- Validate all input with Zod on the server (actions and route handlers)
- Auth checks in middleware AND in each server action/query; UI hiding is not security
- Rate-limit public form and checkout endpoints
- `.env.example` listing: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SITE_HOST`, `NEXT_PUBLIC_PORTAL_HOST`, `PAYMENT_PROVIDER`, PayMongo keys, email provider keys, Turnstile keys
- Treat personal data carefully (emergency contacts, blood type, phones, donor info). Minimize exposure; log exports. Mention Philippine Data Privacy Act compliance basics in `docs/PRIVACY-NOTES.md` (consent text on forms, data retention, a contact for data requests), flagged as needing review by the organization.
- Timezone `Asia/Manila`; currency PHP; timestamps as `timestamptz`
- Error, loading and empty states on every page
- Tests: Vitest for validators, role helpers, price/stock logic; Playwright smoke tests for (1) application submit, (2) checkout with manual payment, (3) donation submit, (4) member login and RSVP, (5) member blocked from admin routes, (6) public host cannot reach portal routes. Add an RLS test script (SQL or pgTAP) proving the key policies.
